# M2 proposed clinical-rule and source approval workflow

**Status:** Governance proposal only. No clinical rules are defined or approved by this document.

## Rule lifecycle (future M6 control)

1. **Request:** A named clinical owner proposes a clinical question and identifies the intended population and setting.
2. **Source selection:** Record the exact guideline/source, edition, publication/effective date, jurisdiction, applicable sections and reuse permission.
3. **Clinical interpretation:** A qualified reviewer documents intended meaning, inclusion/exclusion conditions, required inputs, units, missing-data behaviour and limitations. The software team does not create the medical interpretation.
4. **Specification:** Convert the approved interpretation into a deterministic, versioned rule specification. Keep clinical logic separate from generated prose and model behaviour.
5. **Independent review:** Clinical reviewer checks the specification and expected cases. The required institutional reviewer/approval arrangement must be determined with the clinic; this document does not invent a universal staffing rule.
6. **Engineering verification:** Implement typed deterministic logic and tests for normal, boundary, invalid-unit, missing, conflicting, stale and excluded inputs. The LLM cannot create or edit rule outcomes.
7. **Release approval:** Named clinical owner and designated product/change authority approve the exact version, source, tests, intended setting and release notes before activation.
8. **Controlled release:** Deploy only to an approved environment and scope. Record version, effective date, deployment and rollback target.
9. **Monitoring and change:** Track source updates, incidents, user feedback and rule performance. Suspend/withdraw a rule when its source is superseded, permission lapses, a safety concern is found or approval is withdrawn.

## Minimum version record

- Rule ID and semantic version.
- Named clinical owner/reviewer and approval date.
- Intended use, user, setting and target population.
- Inclusion/exclusion criteria and required input definitions.
- Exact source title, edition, jurisdiction, section/page, effective date and rights status.
- Deterministic input/output schema and units.
- Missing/conflicting/stale/out-of-range behaviour.
- Tests and clinician-reviewed expected results.
- Known limitations and residual risks.
- Release, suspension, rollback and supersession history.

## Non-negotiable controls

- No rule without an approved source, explicit scope and recorded clinical approval.
- No numeric clinical thresholds authored by engineering or generated by an LLM.
- No model may alter, overwrite or silently reinterpret deterministic rule outputs.
- If source, required input, unit conversion, verification or approval state is uncertain, the future workflow must abstain and explain the failure; final behaviour requires clinical review.
- This process is a proposed governance design and must be accepted by the future clinical reviewer and institution.
